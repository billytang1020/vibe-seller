# 抖店单品直降 — 定时批量促销设计

面向抖店（`fxg.jinritemai.com`）的「单品直降（限时限量购）」批量能力：
定时扫描候选商品、由 agent 判断折扣、**执行前阻塞等用户确认**、分批
提交、回读校验。功能对标市面上的商家浏览器插件，但形态是服务端托管的
定时任务，不是插件。

> 本文是设计定稿，实现尚未落地。除「待验证风险」一节外，其余结论可直接
> 作为编码依据。

## 为什么不做浏览器插件

参考的商家插件（以下称「参考插件」）寄生在抖店页面里，借浏览器 cookie
直接调抖店后台接口。它的能力上限由此决定：只能活在用户当前那个浏览器
窗口，人必须坐在电脑前手动点一次批量，跨次无记忆，改错了没有服务端可
以追溯。

vibe seller 的形态相反 —— 按店铺隔离的托管浏览器会话、定时触发、多店铺
并发、闸门与审核台。**若只是把参考插件的按钮搬进来，得到的是一个更慢
更重的插件**；真正的增量是「每周自动选品 + AI 定折扣 + 人工确认 + 可
追溯」。选品和定折扣是插件结构上做不到的事。

## 地基：登录态复用为什么成立

抖店后台每一次人工点击，背后都是一个 HTTP 请求，凭证在浏览器 cookie
里。`browser-harness` 提供的 `js('<javascript>')` 在**页面上下文**执行
JavaScript，因此 agent 的 `fetch` 与商家本人点出来的请求在服务器看来
没有区别 —— 参考插件赖以生存的能力，vibe seller 本来就有。

两条推论：

- **必须停在抖店域内。** 一旦导航离开 `fxg.jinritemai.com`，cookie 带
  不过去，整套方案失效。参考插件把自己的面板盖在抖店页面上而非跳到自
  家域名，正是这个原因。
- **不必在「点 UI」和「调接口」之间二选一。** 用 agent 做导航与登录态
  保障，用页面内 `fetch` 做批量，两者兼得。

## 核心设计：两层审批

需求是「每周自动跑，但每周都要我确认」。vibe seller 的 plan mode 定时
任务是**创建时审一次、计划冻结、之后每次触发复制冻结计划并跳过规划**
（见 `app/plan_states.py` 与 [subsystems.md](subsystems.md#plan-at-creation-lifecycle)）。
只用 plan mode 的话，用户只在第一次看到计划，之后每周它自己就改价了。

原因在于两样东西的变化频率不同：**方法**（怎么选品、折扣怎么算、红线
在哪）每周不变，**清单**（本周具体哪些商品、各打几折）每周都变。因此
分两层，各防一类错：

| 层 | 时机 | 冻结/审的东西 | 防的错 | 机制 |
|---|---|---|---|---|
| 方法审批 | 创建 schedule 时 | 选品规则、折扣公式、红线 | 策略错 | plan mode（`Schedule.plan` 冻结） |
| 清单审批 | 每周运行时 | 本周商品清单与目标价 | 这一次错 | 执行前阻塞确认卡 |

两层不冗余。少了方法审批，每周都要从头讨论策略；少了清单审批，定时任
务会无人值守地改价。

### 清单确认卡：复用 vision 的确认注册表

`app/vision.py` 的确认卡（AI 出图前等用户确认）是现成同构模板，三条不
变式必须一并继承，它们都是踩过坑换来的：

- **永不超时。** 像 `AskUserQuestion` 一样单纯等用户。促销场景尤其不能
  加超时兜底 —— 「超时即执行」等于绕过闸门，「超时即放弃」会让凌晨触发
  的任务在用户起床前静默失败。
- **单任务单待确认。** 同一任务的新请求 supersede 旧的，UI 永不出现两
  张活卡。
- **重连可恢复**（`get_pending_request(task_id)`）。这条对定时任务是生
  死线：任务可能凌晨触发并挂起等待，用户次日才打开界面。卡片若不能重
  新下发，任务永久阻塞。

确认卡至少要展示：商品数、SKU 总数、每个商品的原价与目标价、最大跌幅、
批次数与预计耗时、本次选品依据。用户应能**逐行剔除**后再确认，而不是
只能全批同意或全批拒绝。

## 为什么价格红线不能放在 stop gate 里

`app/ai/stop_gates/__init__.py` 的闸门是**软的**：模块级 `_attempts`
按 `(task_id, gate_name)` 计数，agent 拒绝一次后有一次修正机会，**第二
次调用就放行**（stall fail-open，避免弱模型被卡死在做不完的活上）。只
有 `GateDeny.contradictions` 这类「不可能为真」的项要求持续拒绝。

这个默认对报告完整性是对的，对改价是错的：软闸门意味着 agent 重试一次
就能把越线的价格送出去。

更根本的一点 —— **改价是 `browser-use` 直接产生的事实，stop gate 只是
交活时的事后检查。** 一个没加载 promotion skill 的任务，闸门根本不注册
（闸门骑在 skill 的 `gates:` frontmatter 上），但它照样能改价，只是没人
拦。广告闸门的 fail-safe 方向是「没声明就不输出建议」，安全；**促销的
fail-safe 方向是反的**。

因此红线分三道，顺序不可颠倒：

1. **执行前阻塞确认**（agent 绕不过的必经 MCP 工具）—— 硬拦，越线的目
   标价在这里就不允许提交。
2. **提交时逐条自检** —— 每个批次发出前再算一次跌幅。
3. **stop gate 验收** —— 事后比对「声明要改的」与「实际改成的」，配合
   回读校验。软闸门在这一道是合适的。

## 闸门映射：促销就是广告审计的同构问题

`app/ai/stop_gates/` 下已有一套经过实战的高危动作约束，直接映射：

| 现有广告闸门 | 促销场景含义 | 参考插件的对应物 |
|---|---|---|
| `ad_declaration` / `ad_scope` | 先声明活动类型 + 商品范围 | 无 |
| `ad_bid_floor` | 活动价不得低于原价某比例 | 「误操作防范 30%」 |
| `ad_execution_fidelity` | 声明要改的 vs 实际改的 | 无 |
| `ad_change_cooldown` | 同一商品不得反复上活动 | 无 |
| `ad_writeback_backing` | 每个折扣要有数据依据 | 无 |
| `ad_completeness_review` | 批次完整性 + 审核台 | 「处理结果」列 |

参考插件只有第二行，且是硬编码常量。其余五行需要服务端、跨次记忆与验
收能力，插件结构上做不到。

**申报沿用 append-only 语义**：声明先于动作，同一轮内的再声明不得放宽
范围（见 `app/ai/ad_declaration.py` 的 in-turn ratchet）。促销的「放宽」
指扩大商品集或下调价格下限，两者都必须拒绝。

## 批次形状：被三个约束同时夹住

`browser-harness` 给每次 `browser-use` 调用套 **120 秒硬闹钟**，且连续
两次超时会被判定为浏览器卡死，打印 `UNRECOVERABLE` 并要求 agent 停止重
试。因此：

- **循环写在 shell 层，不在 heredoc 里。** 每次调用只做一个单元（拉几
  页商品 / 提交一个批次）。
- **每步结果立刻追加落盘**，让进度跨调用存活。
- 超时会让标签页停在操作中途，**下一次调用开头必须重读状态**，不能假
  设上次停在哪。

批次大小取三者最严：平台限额（每活动 ≤100 商品、SKU 总数 ≤2000）、风控
节流（参考插件默认 3 秒活动间隔）、120 秒超时。

## 落盘契约：不要信 agent 的报告

`app/ai/review_manifest.py` 记录了一条应当照搬的原则：闸门的契约虽是
`check(result_text, ...)`，但报告是 agent 写给人看的摘要，**可以与它实
际做的事完全脱钩**。所以闸门验的是落盘的结构化数据，不是报告文本。

数据落在**任务级**工作区 `~/.vibe-seller/tasks/<task_id>/promo/`：
`retry` 会清空它，于是「文件存在 ⟺ 本次运行产生」，新鲜度成为结构性保
证，无需 `collected_at` 之类可被游戏的启发式（agent 能保留旧文件或重盖
时间戳）。

`promo/v1` 契约草案：

```json
{
  "schema": "promo/v1",
  "store_slug": "example-store",
  "kind": "create",
  "scope": "products",
  "declared_at": "2026-01-05T02:00:00Z",
  "price_floor_pct": 30,
  "candidates": 1000,
  "selected": 37,
  "batches": [
    {
      "batch_no": 1,
      "activity_name": "auto-20260105-01",
      "items": 37,
      "sku_total": 214,
      "submitted_at": "2026-01-05T02:14:00Z",
      "verified_at": "2026-01-05T02:16:00Z"
    }
  ]
}
```

每个商品一条记录（`promo/items/<product_id>.json`）：商品 id、原价、目
标价、跌幅、SKU 数、选品依据、提交状态、**回读校验结果**。

**回读校验是独立一步**：提交成功的响应只证明请求被接受，不证明活动价
生效。必须从抖店重新读一遍活动，与 `target_price` 逐条比对，写入
`verified_price`。`ad_writeback_backing` 的思路即是如此。

## 定时 + 多店铺：cursor 的已知陷阱

`app/models/schedule_state.py` 把 `store_id` 放进主键，是一次真实事故
的修复：fanout schedule 的兄弟任务共享 cursor 时，后写的覆盖先写的，其
他店铺读到别人的值就跳过自己的工作。

促销 cursor（如「上次上活动的商品集」「上次运行时间」）必然是**按店铺**
的，写入时务必带上 `store_id`，不要用 `NO_STORE_SCOPE`。`ad_change_cooldown`
这类冷却判断依赖它，串了就会让某个店铺的商品被反复上活动。

## 待验证风险

以上设计不依赖下面这个问题的答案，但它决定第一行实现代码能否写：

**抖店的商品列表 / 活动创建接口，在页面上下文里用 `fetch` 调用时，签名
与风控参数能否自动带上？**

若这些参数由页面 JS 动态生成后注入请求，则 `fetch` 会被拒，只能退回逐
格点 UI。那样在 120 秒节奏下每周处理数百商品基本不可行，产品形态需重新
设计。

验证路径（纯只读，零风险）：建一个抖店 store，手工登录一次种下 cookie，
跑一个任务让 agent 导航到限时限量购创建页，用 `js()` 调一次商品列表接
口并打印前几条。成功即继续，失败即重新评估形态。

## 实施顺序

1. 只读验证上述签名问题（唯一的形态决定项）
2. `doudian-shared`：登录 + 导航 + 店铺身份
3. 只读的候选商品枚举与过滤，落盘 `promo/v1`
4. 清单确认卡（阻塞式，含三条不变式）
5. 分批提交 + 回读校验
6. 促销闸门（价格下限 / 执行保真 / 冷却）
7. schedule 接入（方法审批走 plan mode，按店铺 cursor）

只读部分（1–3）没有任何写操作，可以放心先跑通；第 4 步在第 5 步之前落
地，保证「能改价」这个能力从第一天起就在闸门后面。
